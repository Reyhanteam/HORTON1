# HORTON Notifications & Broadcasts

## Scope

Horton has two separate outbound messaging paths:

1. **Notifications** — transactional/user-specific events generated by the application domain.
2. **Broadcasts** — administrator-authored messages sent to a selected audience.

Telegram remains a delivery transport. Domain code does not route business logic through Telegram controllers.

## Database

The existing `notifications` and `notification_deliveries` tables are reused. Migration `2026_09_13_000004_add_notification_deduplication_and_broadcast_recipients.php` adds:

- `notifications.deduplication_key` — unique idempotency key for one logical notification.
- `broadcasts.targeting` — persisted audience definition.
- `broadcasts.batch_size` — configurable recipient batch size.
- `broadcast_recipients` — per-user broadcast delivery state, attempts and errors.

No existing notification table was duplicated.

## Notification text

Every notification title/body is resolved from `bot_messages` through `BotMessageStore` using:

- `notifications.<type>.title`
- `notifications.<type>.body`

No Telegram notification copy is hard-coded in the Telegram layer. The SQL catalog is in `docs/database/notification-message-data.sql`.

## Thirty notification types

- Account: registration success, phone verification success, account status changed.
- Payments: success, failed, pending manual payment, manual approved, manual rejected.
- Wallet: credited, debited.
- Orders: created, processing, completed, failed.
- Services: expiring in three days, expiring in 24 hours, expired, renewal success, renewal failed, created, provisioning, capacity increased, disabled, reactivated.
- Marketing: discount applied, gift redeemed, referral reward, cashback credited.
- Support: ticket replied, ticket status changed.

## Delivery and reliability

`SendTelegramNotificationJob` is queued, unique per notification and uses the shared HORTON queue policy. Delivery attempts are persisted in `notification_deliveries`. Telegram API errors are rethrown so Laravel/package retry behavior remains effective.

Broadcasts are prepared by `QueueBroadcastJob`, then delivered by one unique `SendBroadcastRecipientJob` per broadcast/user pair. This prevents a retry from creating duplicate recipient jobs or duplicate successful sends.

## Service expiry

`horton:notifications:dispatch` runs every five minutes. It:

- marks expired active services as `expired` and sends the expired notification once;
- sends the three-day reminder while the service is inside the configured three-day window and still beyond the configured 24-hour threshold;
- sends the 24-hour reminder for services expiring within the configured 24-hour threshold;
- queues scheduled broadcasts.

Deduplication keys make reminder dispatch idempotent across scheduler retries.

Settings are stored in `bot_settings` and read through `SettingsStore`:

- `notifications.enabled`
- `notifications.service_expiry.3_days.enabled`
- `notifications.service_expiry.3_days.hours`
- `notifications.service_expiry.24_hours.enabled`
- `notifications.service_expiry.24_hours.hours`

## Admin boundary

Broadcast creation, scheduling, targeting, queueing and cancellation are exposed only through authenticated admin routes. Notification history and delivery state are also admin-readable. No notification or broadcast administration is exposed inside Telegram.

## Edit-message rule

Interactive Telegram screens continue to use `BotMessageResponder`, which edits the current bot message whenever an incoming update has a usable bot message state. Proactive notifications and broadcasts are intentionally **new outbound messages** because there is no incoming bot message to edit. This does not replace or weaken the edit-first architecture for normal bot UI.

## Targeting

Broadcast targeting currently supports persisted filters for:

- user status;
- locale;
- presence/absence of an active service;
- presence/absence of a trial service.

Only users with an active Telegram account are eligible recipients.

## Queue workers

Default configuration places notifications and broadcasts on the same `HORTON_QUEUE_NAME` queue. They can be separated with `HORTON_NOTIFICATIONS_QUEUE` and `HORTON_BROADCAST_QUEUE`. If separate queues are configured, workers must consume all configured queues.
